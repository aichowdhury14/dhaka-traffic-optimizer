# Dhaka Traffic & Public Transport Optimization

Data engineering + ML project for corridor-level congestion analysis and
route planning in Dhaka, Bangladesh, built on a real OpenStreetMap road
network.

Two parts:

- **`src/`** — the Python data pipeline: fetches Dhaka's real road network,
  resolves major corridors onto it, simulates rush-hour-calibrated traffic
  (or pulls a live signal), and exports everything the web app needs.
- **`web/`** — the deployable product: a Next.js dashboard (map, heatmap,
  trends, "best time to travel" advisor), built to run on Vercel with zero
  configuration and upgrade transparently to live data once a database and
  TomTom key are wired up. **This is what you deploy.**

There's also a standalone Streamlit dashboard (`src/dashboard/app.py`) from
an earlier iteration — kept for local exploration, but `web/` is the
actively developed, deployable version.

## Architecture

```
OSM road network (osmnx)  →  corridor routes (real geometry)
                                     │
                                     ▼
                    traffic signal (simulated now, TomTom later)
                                     │
                                     ▼
                    SQLite (local) / Neon Postgres (deployed)
                                     │
                    export_web_seed.py bakes a JSON snapshot
                                     │
                                     ▼
                  web/data/*.json  →  Next.js app (web/)
                                     │
                          ┌──────────┴──────────┐
                          ▼                      ▼
                 API routes (live-or-seed)   MapLibre map, charts,
                                              travel advisor
```

The Next.js app never talks to the Python pipeline directly — it reads the
bundled `web/data/*.json` seed files (regenerated by
`export_web_seed.py`) unless `DATABASE_URL` is set, in which case it reads
live Postgres instead. Same API routes, same components, either way.

## Python pipeline setup

```bash
python -m venv .venv
.venv/Scripts/activate   # Windows
pip install -r requirements.txt
```

Steps 1-2 hit OpenStreetMap/Overpass and are slow (large metro-area query) —
run them once, then re-run steps 3-4 as often as you like.

```bash
# 1. Download and cache Dhaka's drivable road network (one-off, slow)
python -m src.ingestion.fetch_road_network

# 2. Resolve configured corridors (src/config.py) to real routes on that graph
python -m src.ingestion.build_corridors

# 3. Simulate traffic history + load into local SQLite
python -m src.pipeline.run_pipeline --days 30

# 4. Export corridors + traffic + baseline as JSON for the web app
python -m src.pipeline.export_web_seed
```

Forecasting model comparison (historical baseline vs. XGBoost):

```bash
python -m src.models.forecast
```

## Running the web app

```bash
cd web
npm install
npm run dev
```

See [`web/README.md`](web/README.md) for the full stack breakdown,
environment variables, and Vercel deployment steps.

## Project layout

- `src/config.py` — corridor definitions (edit to add/remove routes)
- `src/ingestion/` — OSM fetch, corridor resolution, traffic simulation
- `src/pipeline/` — storage layer, end-to-end runner, web seed exporter
- `src/models/` — forecasting
- `src/dashboard/` — legacy Streamlit app (local-only, not deployed)
- `web/` — Next.js app (map, charts, API routes) — deploys to Vercel

## Swapping in real traffic data

Locally, add a `TOMTOM_API_KEY` to `.env` (see `.env.example`) and write a
`src/ingestion/fetch_tomtom_traffic.py` that outputs the same columns as
`simulate_traffic.py`. In the deployed app, this is already wired up:
`web/app/api/sync-tomtom/route.ts` pulls TomTom data into Postgres on a
schedule (Vercel Cron, hourly by default) once `TOMTOM_API_KEY` and
`DATABASE_URL` are both set — no code changes needed.
